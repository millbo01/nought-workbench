# Nought Engine: handover

A self-contained description of the Nought Engine as built, for a model that has not seen the repository. It reflects engine 0.4.0 and schema 0.4.0 (2026-10-20), after James's answers to the first open questions, his approval of P-LOAD-01's form, the 0.4.0 migration (docs/decisions.md, decision 12: the versions, and loads required to be non-negative), the optional work extension P-WORK-01 and P-DEP-01 (approved 2026-10-20 as optional modelling proposals, not CANON), and the tracking-only backlog ledger P-LOAD-02 (approved 2026-10-20, an optional proposal).

**Ground rules:**
- The specification is CANON.md (SHA-256 `dd3a6ccaa20db6760364320617447824794134190249d1e974ea126fde351266`). It wins over this file and over everything in the code.
- APPLICATION.md (SHA-256 `e6673fbe240170bd660a9c95bddfedc5e8842170d6c54dc852ff4ff942df0f1d`) holds application rules James has mostly not agreed; it is a source of proposals, not a specification.
- The engine invents no theory. Where CANON gives no rule, a calculation is refused inside the result, or a named proposal supplies it. Every run lists the proposals in force.

**What the engine is:** a pure TypeScript function from a model (a mapped system) and a scenario (a load applied to it) to an exact, canonical trace. It has no I/O, clock, randomness or globals. Arithmetic uses exact rationals (BigInt), and the trace is canonical JSON with a SHA-256 fingerprint. There are no runtime dependencies, and it runs in a browser or on a server.

**Core terms:**
- **The shared flow:** each resource has one shared flow per step, into which inflow, outside input and store releases enter.
- **Access:** each part's access to the shared flow is limited separately, by a **setting**. A setting is a declarative rule giving access at each sensed level.
- **The governor:** holds **bands** on sensed **levels** and does no work. Each level is produced by a part.
- **Shortfall:** a count at a part: requirement minus amount received, where positive. Requirement is upkeep plus work.
- **The top:** one part, fixed by the boundary. The **protected flow** is what the top receives of the protected resource, measured against its need (its requirement).
- **Snapshots:** steps are grouped into snapshots; a new one starts at a mode change or an arrangement revision.

## 2. Validation rules

A model or scenario that breaks an **error** rule cannot be initialised: `run` throws `ModelInvalidError` with every issue and its path. A **flag** is reported and the run goes ahead. Codes are shown in brackets.

### Shape (every document)
- [type], [missing-field] A field has the wrong JSON type, or a required field is missing.
- [unknown-field] Any field the schema does not define is rejected, so a typo never becomes a default.
- [bad-id] Ids match `^[A-Za-z0-9][A-Za-z0-9_.:-]*$`.
- [bad-number] A number is a finite JSON number, a decimal string ("12.5", "1e-3") or a fraction string ("3/4").
- [bad-gap] An information gap is written `{ "gap": "<note>" }` with a non-empty note, and only where the schema allows a gap.
- [bad-measure] A level measures `store-content`, `load`, `received`, `entering` or `inflow` (C7.1c).
- [schema-version] Model and scenario state schema version 0.4.0 (the engine reads no other).
- [incomplete] The document is missing a required top-level part.

### Components and structure (model)
- [one-boundary] Exactly one boundary per model (C2.1).
- [one-top] The boundary names exactly one top, which is a part; no part carries its own `top` field (C2.1, C2.3d). The top may be an explicit gap (flagged).
- [governor-not-part] The governor is never a part: no units, requirement, upkeep, rank, access or loads; not a part id; never a level's producing part, in a dependency, given access or routed to (C2.2c, C3.1).
- [units-belong-to-part] Units appear only on parts (C3.10).
- [part-field-on-non-part] Requirement, upkeep, rank, access and loads appear only on parts (C2.3a).
- [units] A part's units are a whole, non-negative count (C3.10).
- [duplicate-id] One id namespace across all components and mapping aids; loads are unique within a part.
- [unknown-reference] Every reference names something that exists.
- [duplicate] A part states requirement (or upkeep) at most once per resource.
- [upkeep-without-requirement] Upkeep is stated only for a resource the part requires (C3.11b).
- [upkeep-exceeds-requirement] A constant upkeep is not above a constant requirement: requirement is upkeep plus work (decision Q-023).
- [requirement-monotone] A requirement rule never falls while its inputs rise: no negative coefficient, no falling table (C3.12b).
- [requirement-reads-units] A requirement rule cannot read units (C3.12c).
- [negative] No rule, capacity, amount or series value is negative where a quantity is meant. This includes every load value in a scenario (from schema 0.4.0); a gap stays allowed.
- [bad-rule] Step tables have at least one step with strictly increasing thresholds; linear tables have at least two points with strictly increasing `at`.
- [draws-not-separate] `draws` is given only on a part that sets its own access.
- [missing-field] (separate case) A part that sets its own access states the resources it draws, or an explicit gap (C3.5).
- [self-set-access] (flag) A part that sets its own access is a separate case: excluded from ranking and not computed (C3.5).
- [dependency] A part cannot feed itself.
- [rank-layer] A declared layer must equal the layer derived from dependencies (C4.3a).
- [rank-unreached] (flag) A part with no dependency path to the top sits in the bottom layer (decision Q-017).
- [band] A band's lower limit is not above its upper limit; a held value lies inside the band (C2.2a, C2.2n1); at most one band per level.
- [band-missing] A mode holds only levels the governor has a band on (C2.2a).
- [level-producer] Every level names an existing part as its producer (C3.1a, C7.1a).
- [level-route] Every level names its signal route: its own route, or the shared flow of a resource (C7.1b).
- [missing-field] (level) Every level states how silence is read: `no-intervention` or `alarm` (or a gap).
- [sending-dial] A sending dial is `keeps-sending` or `stops-when-short`. A stopping dial states one amount for each resource the producing part requires, and none for anything else (decision Q-004, PROP-SENSE-01).
- [resource-mismatch] A level's unit equals the unit of what it measures (no arithmetic across resources).
- [setting-kind] A governor-set setting, store rule or route capacity is among what the governor controls; a built-in one is not (C3.6a, C3.7, C3.8n).
- [setting-without-requirement] A setting gives access only to a resource its part requires (write requirement 0 if it requires none).
- [silence-no-intervention] A rule cannot state a value for silence read as no intervention: the governor does not act.
- [mode-settings] A mode has at most one setting per part per resource: access is set as a whole (C3.11a).
- [missing-setting] Every mode gives every non-separate part a setting for each resource it requires.
- [indicator-kind], [indicator-watches] An indicator states its kind and watches one thing. A protected-flow indicator watches the protected flow; a held-level indicator watches a level held in at least one mode; a "neither" indicator does not watch the protected flow (C3.3).
- [protected-flow] The top has a requirement for the protected resource (C2.4).
- [no-part-to-part-route] No route runs from a part (C3.4a).
- [route-not-from-shared-flow] Routes run from the shared flow to parts only; `from` is omitted or `"shared-flow"`. A store or outside input as a source is rejected: they enter the shared flow, and a ring-fenced allocation is a built-in access setting on the receiving part (decision Q-010).
- [route-limit] At most one route per part per resource (engineering limit).
- [store-not-storable] A store holds only a resource marked storable (C2.6).
- [switch-not-mode-change] (flag) A threshold switch whose target mode changes neither the order nor the held levels (C4.4n1); the run labels it an arrangement revision.
- [gap] (flag) An information gap on the top or the protected resource; every result that depends on it is refused.
- [load-dial] P-LOAD-01's dials, checked whenever present. The unit-loss dial names at least one resource, each one the part states upkeep for, at a non-negative rate. The rebuild dial states a non-negative `perStep` and at least one resource the part requires, at a positive cost per unit.

### Scenario (against its model)
- [scenario-model] The scenario names its model's id.
- [scenario-not-system] A scenario declares no components: it is a load applied to a system (APPLICATION 5, proposal APP-04).
- [inflow-missing] Exactly one inflow series per resource (write 0 where nothing enters).
- [outside-input-missing] Exactly one series per outside input.
- [load-missing] Exactly one series per declared load on each part.
- [load-supplied] With the internal option for loads a coupling supplies (P-COUPLE-01; never used by `run()`), such a load has no series in the scenario, so that it has one source. Every other declared load still needs exactly one series.
- [series-start], [series-order] Every series starts at step 0, with strictly increasing steps.
- [series-after-end] (flag) A series entry after the last step.
- [initial-store] Exactly one initial content per store.
- [store-capacity] A store does not start above its capacity.
- [initial-reading] Initial readings are given only for levels that measure the step before.
- [initial-reading-missing] (flag) A level measuring the step before with no initial reading is refused at step 0.
- [event-after-end] Events fall within the run.
- [empty-intervention] An intervention changes the mode, settings, held levels or a band.
- [proposal-disabled] A scenario cannot enable P-IPF-01 to P-IPF-06.
- [unknown-proposal] A scenario can enable only P-LOAD-01.
- [load-dials-missing] (flag) P-LOAD-01 is enabled but no part sets its dials.

### Proposal data checks (flags, labelled with the proposal)
- [grading] (P-ALLOC-01) Every setting of a part other than the top carries a positive grading.
- [grading-order] (P-ALLOC-01) Within a mode and resource, a lower-ranked part's grading is no smaller than a higher-ranked part's.

### Work attachment (P-WORK-01, P-DEP-01; against its model)
A work attachment that breaks an error rule stops `runWork` before the base run, with `ModelInvalidError`. It reuses the shape codes above ([unknown-field], [missing-field], [type], [bad-id], [bad-number], [bad-gap], [duplicate-id], [unknown-reference], [negative], [bad-rule]) and adds:
- [work-version] The attachment states format 0.1.0.
- [work-model], [work-model-digest] It names the model's id and that model's exact digest, `RunStamp.mapping.sha256` (decision 10).
- [work-proposal] It enables P-WORK-01, and only P-WORK-01 and P-DEP-01, each at version 0.3.
- [work-link-proposal] Links need P-DEP-01 enabled.
- [work-rule] A reference-output rule is constant, linear or table (decision 6).
- [work-reference-monotone] A reference-output rule never falls while its load rises: no negative coefficient, no falling table (P-WORK-01, not Q-009).
- [work-recipe] A recipe lists at least one resource, each amount above 0.
- [work-recipe-resource] A recipe resource is one the part requires.
- [work-recipe-upkeep] The part states upkeep for each recipe resource, 0 allowed (decision 4).
- [work-capacity] A capacity is a constant with a rationale, or a per-unit amount.
- [work-yield] A yield lies in [0, 1].
- [work-link-dependency] A link matches an existing dependency (the link's `part` feeds its `feeds`).
- [work-link-endpoint], [work-link-units] Both ends have a work, in the units the link names.
- [work-ratio] A ratio is above 0.
- [work-link-semantics] Semantics is `non-exclusive-enablement` or `exhaustible-support`.
- [work-separate-case] (flag) A work on a part that sets its own access: its resource term and any per-unit capacity are refused.
- [work-several-on-part] (flag) Several works on one part: they are refused (decision 8).
- [work-link-lag] (flag) A lag above 0: refused when computed (D-3).
- [work-link-exhaustible] (flag) Finite shared support: refused when computed (D-4).

### Backlog attachment (P-LOAD-02; against its model and work attachment)
A backlog attachment that breaks an error rule stops `runBacklog` before any run, with `ModelInvalidError`. It reuses the shape codes above ([unknown-field], [missing-field], [type], [bad-id], [bad-number], [bad-gap], [duplicate-id], [negative], [series-start], [series-order]) and adds:
- [backlog-version] The attachment states format 0.1.0.
- [backlog-proposal] It enables P-LOAD-02 at version 0.1, and nothing else.
- [backlog-model], [backlog-model-digest] It names the model's id and that model's exact digest.
- [backlog-work-attachment] It names the work attachment by id, version and exact digest, and that work attachment names the same model.
- [backlog-digest] A digest is 64 lower-case hex digits.
- [backlog-account-work] An account names a part and a work the work attachment maps.
- [backlog-double-registration] One account per part and work.
- [backlog-unit] The obligation unit is exactly the work's unit.
- [backlog-divisibility] Divisibility is stated: `indivisible` or `divisible`.
- [backlog-integral] An indivisible account's opening balance and admissions are whole counts (no rounding).
- [backlog-closure] The closure claim states `oneToOne: true`.
- [backlog-withdrawals] The withdrawal claim states `zeroEveryStep: true`; an omission is not a zero.
- [backlog-evidence] Evidence is `documented`, `estimated`, `assumed` or `unknown`, with a source.
- [backlog-unknown-claim] (flag) An unknown claim: what depends on it is refused.
- [backlog-conditional] (flag) An assumed or estimated claim: the account's results are conditional on it.

## 3. The simulation-step sequence

### Initialisation
1. Parse and validate the model, then the scenario against it. Any error: throw `ModelInvalidError`.
2. If the allocation policy given is a disabled proposal (P-IPF-01 to P-IPF-06), or is P-LOAD-01 (not an allocation policy): throw `ConfigurationError`. With no policy, the run goes ahead and every draw is refused. P-LOAD-01 is on for the run only if the scenario's `enable` list names it.
3. Digest each document (SHA-256 of its canonical JSON) for the stamp.
4. Derive rank layers from dependencies. Layer 0 is the top; layer k holds parts whose work feeds layer k-1. Parts with no path to the top go in the bottom layer, the deepest reached and at least 1. Separate cases are not ranked.
5. Initial state:
   - the arrangement is the initial mode (its held levels, its settings, and positions from the mode's order or else each part's rank);
   - the bands are the governor's;
   - store contents are the scenario's initial contents;
   - unit counts are the parts' counts.
   There are no step-before values.

### Within step t (t = 0, 1, ..., steps - 1)
1. **Events at t,** in the order the scenario lists them:
   - **Damage** marks the part damaged for the rest of the run (refused: unsupported rule, Q-015).
   - **Interventions:**
     - `setMode` puts a declared mode in force, and clears an unknown arrangement.
     - `replaceSettings` and `setHeld` make a derived arrangement `<mode>~step<t>`. If the arrangement is unknown, they are refused (invalid settings change) and it stays unknown.
     - `setBand` replaces a band: flagged, not a mode change.
   - **Signal events** (`not-sent`, `filtered-on-route`) apply to this step only.
2. **Sensing**, each level in id order, under the arrangement after the interventions:
   - **True value:** the true (definite) value of what the level measures, as at the start of the step: store content after step t-1 (or initial), loads applied at t, and for "received", "entering" and "inflow" the values of step t-1 (at t = 0, the scenario's initial reading, else refused).
   - **Sent:**
     - If the producing part is a separate case, refused.
     - If the producing part was short in step t-1, or its units are unknown only because of an earlier shortfall, its sending dial decides. "Keeps sending" sends. "Stops when short" is never sent if any of its shortfalls in step t-1 exceeds the stated amount, and otherwise sends. With no dial, the level is refused.
     - If the producing part has no units, never sent. If a scenario event says not sent, never sent.
     - Otherwise it sends the true value.
   - **Delivered:**
     - signal route a gap: refused;
     - filtered on its route: sent but not actionable (route or filtering);
     - arrangement unknown: refused;
     - no band held on the level in this arrangement: sent but not actionable (no held band or action);
     - band held but no rule or switch in force reads it: sent but not actionable (no held band or action), with the delivery recorded;
     - otherwise: produced and delivered.
     Each silent record notes what supports it (the mapping or a scenario event). Nothing is recorded as delivered for a silent level.
3. **Threshold switches,** in id order. Skipped at t = 0, and in a step where an intervention changed the arrangement. For each switch whose `fromMode` matches the arrangement's declared mode (or that has none):
   - **Crossing:** compare the delivered value at t-1 with that at t. Rising: before < threshold <= now. Falling: before > threshold >= now.
   - **Silence at either step:** read as no intervention, no crossing (the governor does not act); read as alarm, the transition is refused as unmapped, and the arrangement becomes unknown.
   - **Several switches** firing towards different modes: unmapped.
   - **One switch** firing towards another mode puts that mode in force, and delivery (step 2) is recomputed under its held levels.
4. **Snapshots:**
   - **Step 0** is the initial snapshot.
   - **Classifying a change:** where an intervention or switch acted in step t, compare the arrangement at the start of the step with the one now:
     - held levels or the order differ: **mode change**;
     - only settings differ: **arrangement revision**;
     - it became unknown: **unmapped**;
     - it is known again after being unknown: **unclassified**.
   - **No difference:** no new snapshot.
   - **Effect:** a new snapshot starts at step t and clears any refusal of the recorded order. A setting acting on a changed level is not a change.
5. **Governor-facing rules,** reading delivered levels only (never the true state):
   - **What is computed:**
     - each part's access to each resource it requires, from the setting in force;
     - each route's capacity;
     - each store's release, then bounded by its content;
     - each store's fill limit, then its room: the lesser of the fill limit and capacity minus content plus release.
   - **A rule reading a silent level:**
     - read as no intervention: the value that rule's target had in step t-1 stands (refused at t = 0, or if that value was refused);
     - read as alarm: the rule's `whenSilent.alarm` value (refused if absent);
     - a built-in rule: refused (unsupported rule, Q-012).
   - **Ranges:** a linear table never extrapolates; a reading outside its declared range is refused.
6. **Requirement and upkeep** for each part and resource, from their rules on the part's loads at t (upkeep may read units).
   - A damaged part's requirement is refused.
   - Check: requirement never falls unless a load it reads fell (otherwise `AccountingError`, a defect).
   - If a built-in part other than the top changes its requirement, the recorded order is refused until the next snapshot (Q-006).
7. **The recorded order:** each ranked part's layer and position (the mode's order, else the part's rank; PROP-RANK-01).
8. **The draw,** per resource in id order:
   - **Entering** = inflow at t + outside input at t + store releases.
   - **Refused if:** a separate case draws the resource; the arrangement is unknown; no allocation policy was given; any value the policy needs is refused; the policy itself refuses (for example a missing grading); or the policy's result breaks a limit.
   - **The limits:** received never above access or route capacity; fills never above room; nothing above what entered; and, where all committed draws (access capped by route) fit within what entered, every part receives its committed draw (decision Q-002).
   - **Otherwise** it gives each part's amount received and each store's fill, and what is left = entering minus received minus fills.
9. **Part accounting,** for each part and resource:
   - realised flow = received;
   - shortfall = max(0, requirement - received);
   - excess = max(0, received - requirement);
   - upkeep covered = min(received, upkeep);
   - remainder for work = received - upkeep covered;
   - work requirement = requirement - upkeep (refused in a step where upkeep exceeds requirement);
   - upkeep shortfall = upkeep - upkeep covered;
   - work shortfall = max(0, work requirement - remainder);
   - which limit bound the draw (access, route, or neither).
10. **P-LOAD-01** (only where the scenario enables it), for each part with both dials:
    - **Loss:** units lost = min(units, the largest over the dial's resources of rate x upkeep shortfall).
    - **Rebuilding:** want = min(units lost so far, this step's loss included, `perStep`). Parts claiming one resource share what was left after parts and stores (step 8) in proportion to cost x want. Each part rebuilds the smallest of want and share / cost over its named resources, and spends rebuilt x cost of each.
    - A part with one dial has its units refused; a part with neither falls under step 12's rule.
11. **Stores:** end = start - release + fill. Outside 0 to capacity: `AccountingError` (a defect).
12. **Resource reconciliation** (store release counted once):
    - **Identity across the step:** opening stock + inflow + outside input = received + mapped outflows (always none) + rebuilding + unused + closing stock.
    - **Identity within the step:** entering = received + fills + outflows + rebuilding + unused, where unused is what is left after rebuilding. Unused is not carried (PROP-FLOW-01).
    - Both are checked; a failure is an `AccountingError`.
    - **CANON 1's ledger:** gap = total requirement - inflow = (release - fill) + outside input + total shortfall. Given only where nothing was left after parts and stores and no part received above its requirement; otherwise refused (scarcity precondition not met).
13. **Units for step t+1:** under P-LOAD-01 (step 10), units - lost + rebuilt. Otherwise, refused if the part was damaged (Q-015) or short in any resource (Q-016); else unchanged.
14. **Records and flags:**
    - the protected flow (what the top receives, its need, its shortfall);
    - indicators;
    - level records (true value, signal category and basis, what was sent, expected recipients, observed delivery, band, in-band);
    - flags: `excess-received`, `inflow-not-fully-used`, `residual-while-short`, `stored-while-short`, `top-short-another-not` (APP-08), `unreached-part-kept-access` (Q-017), `held-level-silent`, `held-level-out-of-band`, `built-in-requirement-changed`, `band-moved`, `intervention-no-change`.

### Between steps
Carried from step t to step t+1:
- amounts received, entering and inflow (for levels measuring the step before);
- each part's shortness and shortfalls (for the sending dial);
- delivered level values (for threshold switches);
- each governor-facing rule's value (for silence read as no intervention);
- access (for the Q-017 flag);
- requirement and loads (for the monotonicity check);
- store contents;
- unit counts.

The unused amount is not carried. After the last step, the last snapshot is closed and the run stamp is written. The stamp holds: engine and schema versions, the canon fingerprint, mapping and scenario digests, the seed, the step count, the allocation policy, the proposals in force, the modes used and every refusal.

### Refusals in the sequence
A refused value carries refusal ids, each described once in the trace's `refusals` list (with category, CANON row, question, first and last step) and in the stamp. Anything computed from a refused value is refused with the same ids; every independent value is still computed. The engine throws only when it cannot initialise (invalid documents, disabled proposal) or when its own invariants fail.

### The work extension (P-WORK-01, P-DEP-01): after the run, apart from it
`runWork(model, scenario, attachment, options)` validates the attachment, runs the unchanged `run()` once and calls the pure `workFromTrace`, which reads the finished base trace and writes nothing to it. `run()` itself never computes work. For each base step t, parts with a work are taken in dependency order along the enabled links (upstream first, ties by id; the members of a same-step cycle are found first). For each work at part p:
1. **Reference output** from its rule, on p's own loads at t (the scenario series rule of the core, `seriesAt`).
2. **Capacity:** the constant, or the per-unit amount times p's units at the start of t from the base trace.
3. **Available** per recipe resource r: the base trace's `remainderForWork[p, r, t]`, as it stands. **Recipe limit** = available / recipe amount; **resource-limited output** = the least recipe limit; **yielded resource output** = yield x resource-limited output.
4. **Pre-dependency output** = the least of reference output, capacity and yielded resource output.
5. **Caps** from each enabled link A to p: A's actual output / ratio. Refused, as an unsupported rule, for a lag above 0 or finite shared support; refused with the cycle's refusal from another member of p's cycle.
6. **Actual output** = the least of pre-dependency output and the caps; **work not done** = reference output less actual output, never below 0; the **binding** terms.

Every term is 0 or more, so a known 0 settles a minimum, or the product with yield, beside a refused term (decision 5), except where an unsupported rule applies to p's own work or incoming links (several works on p, p in a cycle, a lagged or exhaustible link into p). The work trace carries its own stamp (the base trace's hash, model and scenario digests and versions, the attachment's id, version and digest, the proposals and their versions), the step records, every refusal behind a work value (ids the extension creates start `work/`; base ids are kept), and the open questions behind them.

**Readings and additions, where the texts left a choice:**
- **Known zeros (resolution 5, amendment 2).** The rule covers a minimum, the product with yield, and division by a positive recipe amount or ratio, which the required zero-yield and zero-available tests need. A known 0 overrides a refused value of any origin, including a refusal carried from an upstream part. It never overrides an unsupported rule on the record's own work or its own incoming links: several works on the part, the part in a same-step cycle, or a lagged or exhaustible link into it. So a part downstream of a cycle, with its own capacity known to be 0, has output 0: its own link is supported, and only that link's value is missing.
- **Binding (resolution 5, amendment 3):** refused where the actual output is refused; otherwise the terms known to equal the output, and apart from them the refused terms, labelled `unresolved`.
- **A reference output below 0** is refused (amendment 1). It is a guard: with loads non-negative from schema 0.4.0 and the rule forms of resolution 6, no valid document gives one.
- **Loads are non-negative** for every run, at validation, from schema 0.4.0 (James's ruling, 2026-10-20). It is a core validation change, made in the migration commit.
- **Versions (resolution 12, amendment 4):** the engine and the schema moved to 0.4.0 in one commit, so the golden hashes changed once. The engine reads only 0.4.0 documents. The 0.3.0 hashes are kept in tests/golden/history/0.3.0.json, and a test rebuilds each from a 0.4.0 trace by restoring the four stamp fields that changed.
- **Several works on a part (resolution 8):** the reference output, capacity, yield and available amounts are still reported; recipe limits and everything after them are refused, since each would assume the whole recipe.
- **A part that sets its own access** has no part or unit record in the base trace, so its resource term and any per-unit capacity are refused as a separate case (Q-014).
- **Refusal ids (resolution 9):** every id the work extension creates starts `work/`, including those raised by core helpers while it reads the attachment's own rules (for example a table read outside its range). An unknown load keeps the core's id (`$.loads.<part>.<load>`), the same unknown with the same id the base run would give.
- **Refusal summary:** each refusal is listed once, with its first and last step and how many values it refuses; which outputs it affects is read from the refused values that carry its id.
- **The work step record** copies the base step's mode, not its order.

### The backlog ledger (P-LOAD-02, tracking only): after the work extension, apart from both
`runBacklog(model, scenario, workAttachment, backlogAttachment, options)` validates the model, the work attachment and the backlog attachment, calls `runWork` once, and calls the pure `backlogFromTraces(base, work, attachment, digest)`. That function first checks that the traces and the attachment belong together: engine and schema 0.4.0 and work 0.1.0; the work trace's recorded base hash equals `traceHash(base)`; the attachment's model and work attachment match the stamps; the step counts and units agree. A mismatch is a ConfigurationError. Then, for each account (sorted by id) and each step t:
1. **Opening balance** B_t: the mapped B_0 at step 0 (refused for a gap or an unknown claim), otherwise the closing balance of the step before.
2. **Admissions** N_t: the entry at or before t (the core's series rule; refused for a gap or an unknown claim). **Eligible** D_t = B_t + N_t.
3. **R_t and O_t:** the work record's reference and actual output for the account's part and work, unchanged, with its binding copied as provenance.
4. **Completions** C_t = O_t where every guard holds: the eligibility, closure and withdrawal claims not unknown; D_t, R_t, O_t known; R_t <= D_t; not D_t = 0 with O_t above 0; a whole O_t for an indivisible account. Otherwise refused, with every failed guard.
5. **Withdrawals** W_t = 0, as asserted (refused if the withdrawal claim is unknown). **Closing** B_{t+1} = D_t - C_t - W_t, checked to reconcile exactly.

Nothing is written to the base or work trace, and no ledger value reaches the next step's load, requirement, reference output, draw, units or levels. The backlog trace carries its stamp (the backlog version, P-LOAD-02 and its version, the base run's versions, CANON fingerprint, trace hash, mapping and scenario digests; the work trace's version, hash, attachment and proposals; the backlog attachment's id, version and digest; each account with its claims, evidence and conditions), the records per step and account, every refusal behind a ledger value (ids it creates start `backlog/`; ids from the work trace are kept) and the open questions behind them.

## 5. Proposals

None of these is CANON; each can be withdrawn by James. The stamp lists every proposal in force for a run.

### Questions awaiting James's decision

Twelve questions are open with no ruling yet: seven raised by the work extension (WQ-01 to WQ-07, about the optional proposals P-WORK-01 and P-DEP-01, not about CANON) and five raised in the alignment (Q-027 to Q-031). The kept and parked questions above already have a ruling (keep the current handling, or leave it for a later phase) and are not repeated. Each question below gives why it arises, the options, a recommendation and what it blocks. A recommendation is the engine's, not a ruling.

**WQ-01. Dividing finite support shared by several parts (contract D-4)**
- *Question:* when one part's work is finite support shared by several parts (a ticket resolved for finance is not resolved for scheduling), should P-DEP-01 divide that output between them, and by what rule?
- *Why it arises:* the first release supports only non-exclusive enablement. A link declared `exhaustible-support` is accepted and its recipients' outputs are refused (unsupported rule), as the organisation-shared-support fixture shows. The common organisational case, a shared IT or administration team, is finite and shared.
- *Options:* (a) keep refusing, and map support as non-exclusive only where it truly is; (b) a share stated per link at mapping, the shares from one supporting part summing to at most 1, each recipient capped at its share of the supporting output divided by the ratio; (c) a rule derived from the model, such as rank order or each recipient's reference output.
- *Recommendation:* (b) when a mapping needs it: the mapper states the division, it can be checked, and it adds no theory. (c) would be a new allocation rule. Until then, (a).
- *Blocks:* any mapping of finite, shared support.

**WQ-02. Lagged functional links (contract D-3)**
- *Question:* should a link be able to act with a delay, so that a supporting part's output in one step caps the dependent part's output in a later step; and if so, what caps the dependent part before the first lagged output exists?
- *Why it arises:* P-DEP-01 is same-step only, and a lag above 0 is accepted and refused. CANON 4's lag note (C4.4n2) describes a dependency lag in shortfall, not in work, and Q-007 (what a dependency does) is parked.
- *Options:* (a) same-step links only; (b) a whole-step lag per link, with an explicit starting cap for the first steps (a gap refuses them); (c) same-step and lagged links together on one dependency.
- *Recommendation:* (a) until a mapping needs a delay (for example, maintenance done this week enabling next week's work); then (b), with the starting cap a mapping input and the design checked against C4.4n2.
- *Blocks:* support whose effect arrives in a later step.

**WQ-03. Whether work changes later steps**
- *Question:* should work done or not done change anything in a later step (a backlog carried into the next step's load, a part's physical state, recovery), and through which named rule?
- *Why it arises:* work not done is counted each step and nothing carries. P-LOAD-01's backlog dial exists in the schema and is never read. Any carry-over makes a load, and so a requirement, depend on work: the work extension would then have to run inside the step loop, and the guarantee that work never changes the base run would end for runs that enable it. CANON 3 lets requirement rise with load, and work not done must never lower it.
- *Options:* (a) no carry-over, as now; (b) a backlog: a part's work not done added to one of its loads in the next step, by a stated dial (P-LOAD-01's backlog dial), only in runs that enable it; (c) a wider state-transition proposal covering physical state, damage and recovery.
- *Recommendation:* (a) for this phase. If wanted, (b) first as the smallest step, named as ending the separation from the base run for the runs that enable it.
- *Since:* P-LOAD-02 (2026-10-20) tracks eligible obligations in a ledger of its own, tracking only. Feedback into a later step is still this question.
- *Blocks:* backlog and deterioration scenarios.

**WQ-04. Work as a level the governor senses**
- *Question:* under what evidence standard, if any, may a work quantity (payments completed, appointments booked) become a level the governor senses and holds in a band?
- *Why it arises:* no work value can be a level now (a level cannot measure work), which is how contract test 8 holds. CANON 3 makes sensing work, paid from the producing part's own access. A work level would let output drive access through settings, a loop that needs work inside the step loop, as in WQ-03.
- *Options:* (a) never in this phase; (b) a level may measure a part's work output in the step before (PROP-STEP-01's timing, so no look-ahead), with the cost of sensing it in the producing part's requirement; (c) only observed, recorded work may be sensed, never computed work.
- *Recommendation:* (a) now; if wanted later, (b) with (c) for client work.
- *Blocks:* a governor that responds to output.

**WQ-05. Evidence standards for mapping in paid diagnostics**
- *Question:* which mapped values need documentary evidence before a result is shown to a client, and how should the evidence for each value be recorded?
- *Why it arises:* the work extension adds many mapping claims (recipes, yields, capacities, ratios, and whether support is non-exclusive). The engine records rationales but does not grade evidence, and the fixtures' numbers are hypothetical.
- *Options:* (a) rationale text only, as now; (b) an evidence grade per mapped value (documented, estimated or assumed), carried into the stamp so a result shows what it rests on; (c) (b), plus a rule that a result resting on an assumed value is flagged wherever it is reported.
- *Recommendation:* (c). It changes no calculation, only the schema and the stamp.
- *Blocks:* nothing computational; it decides what may be reported.

**WQ-06. Wider reference-output rules (decision 6)**
- *Question:* should a reference output be allowed to read another part's loads, or to fall as a load rises?
- *Why it arises:* decision 6 limits the first release to non-negative, non-decreasing constant, linear and table rules on the part's own loads, as a restriction of P-WORK-01 to be reviewed before widening. A natural case is finance's payments following the service's caseload.
- *Options:* (a) keep the restriction; (b) allow other parts' loads, still non-decreasing; (c) also allow falling rules, keeping the run-time refusal of a value below 0.
- *Recommendation:* (b): it reads only scenario input, with no loop. (c) only for a stated case.
- *Blocks:* reference outputs driven by another part's workload.

**WQ-07. Deprecating Part.capacity and Part.efficiency (decision 7)**
- *Question:* should the DRAFT fields `Part.capacity` and `Part.efficiency`, never read and superseded by the work attachment, be removed from the model schema, and when?
- *Why it arises:* decision 7 kept them in schema 0.4.0 and ruled out a silent deletion. No fixture uses them.
- *Options:* (a) keep them, unread; (b) flag them at validation now, and remove them at the next schema version needed for another reason; (c) remove them in a schema version of their own.
- *Recommendation:* (b): the golden hashes then change only once, with that other change.
- *Blocks:* nothing.

**Q-027. Mapped outflows or losses**
- *Question:* should resource that leaves other than to parts or stores (a store's spill, a loss on a route, an export across the boundary) be mappable, and as what?
- *Why it arises:* the reconciliation has a `mappedOutflows` term that is always 0, because the schema cannot express an outflow. CANON's components include outside input but no outflow, and everything else is a mapping aid.
- *Options:* (a) none: whatever takes resource is a part (anything that does work), and the rest is unused; (b) a mapping aid for an outflow, with a declarative rule, reconciled as `mappedOutflows`; (c) a store's spill only.
- *Recommendation:* (a) until a model needs an outflow: it adds nothing CANON does not name.
- *Blocks:* models with real outflows.

**Q-028. Arrangement revisions beside CANON 4**
- *Question:* is a change to a fixed access setting that leaves the order and the held levels unchanged a mode change, something CANON 4 should allow for, or a case that cannot arise?
- *Why it arises:* CANON 4 says access settings change only when the mode changes, and CANON 3 defines a mode change by the order or the levels held. The engine labels the case an arrangement revision (a new snapshot, not a mode change); it occurs in the organisation baseline at step 7.
- *Options:* (a) it is a mode change: relabel, and CANON 4 holds as worded; (b) CANON 4 should allow arrangement revisions (a CANON change, James's alone); (c) it cannot arise, because a change of access always changes the order (C4.3b), so the fixture is mapped wrongly.
- *Recommendation:* this is a ruling on theory. For the engine, (a) is the smallest change: labels move, numbers do not.
- *Blocks:* only how snapshots are labelled.

**Q-029. "The governor does not act"**
- *Question:* where silence is read as no intervention, should each rule reading the silent level keep the value it gave in the step before, and be refused where it has none (as at step 0)?
- *Why it arises:* silence never produces a value (alignment item 2), and "the governor simply does not act". The engine reads that as the earlier value standing.
- *Options:* (a) confirm; (b) refuse every rule reading a silent level; (c) a stated default value, which would be silence producing a value, against item 2.
- *Recommendation:* (a).
- *Blocks:* rules reading a silent level at step 0, or after their earlier value was refused.

**Q-030. The catalogue's ids for the engine's own proposals**
- *Question:* does the Unified Core Spec catalogue have ids for PROP-STEP-01, PROP-FLOW-01, PROP-RANK-01, PROP-ROUTE-01, PROP-STORE-01, PROP-SILENCE-01 and PROP-SENSE-01, and what do P-IPF-01 to P-IPF-06 say?
- *Why it arises:* the catalogue is not in this repository, so these ids are the engine's own.
- *Options:* (a) supply the catalogue's entries, and the engine takes its ids; (b) keep the engine's ids.
- *Recommendation:* (a), if the catalogue is to hand. A rename changes every stamp, so the golden hashes change once.
- *Blocks:* nothing; ids only.

**Q-031. P-ALLOC-01 and look-ahead**
- *Question:* is P-ALLOC-01's division of what actually arrives in a step the arithmetic of the shared flow (an arrangement declared in advance), or the governor responding to this step's arrival?
- *Why it arises:* no look-ahead (alignment item 9): the governor reads only levels delivered from the state at the start of the step. If the graded cut were its response, it would be look-ahead.
- *Options:* (a) the flow's arithmetic, as now; (b) the governor's response, so the grading must come from a form that reads only levels from the step before.
- *Recommendation:* (a): the gradings are declared in the settings before the step, and nothing the governor senses in the step enters them.
- *Blocks:* nothing yet; every fixture uses P-ALLOC-01.
